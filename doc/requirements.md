# asuyaru（明日やる）プロダクト要件

休日の前夜に、明日の時間割を組むデスクトップアプリの要件である。
対象は個人、日本語、Mac。

組むのは、その休日のカレンダーである。
次のブロックへ促すこと、当日の飛ばし、残り一日の組み直しは対象外である。

デスクトップの実現手段は未決である。
保存は SQLite ファイル一つである。

---

## 決めたこと

- **休日は計画を作った日である。** 週末や祝日の自動判定はしない。計画を作る行為そのものが「その日は休み」という意味になる。
- **連休でも一日ずつ。** 複数日をまとめて配分しない。連休中は、その日の計画をその都度見る（前夜に翌日分を見る、を毎日繰り返す）。
- **日本語のみ。個人利用。** 他言語も、家族やチームの利用も対象外である。
- **ローカルファースト。** データは手元が先である。SQLite ファイル一つを iCloud に置けば、複数 Mac で同じ DB を共有できる。保存先を「SQLite ファイル一つ」以外に固定して、この共有を塞がない。アカウント製品や汎用クラウド同期にはしない。
- **一日の枠は起床〜「ここまで組む」。** 起床時刻は設定できる。就寝時刻は持たない。ブロックを置ける最も遅い時刻を「ここまで組む」とする。
- **計画は時刻つきの時間割である。** キュー（順番だけのリスト）ではない。各ブロックに開始時刻と終了時刻がある。
- **きつめに組む。** 余白 20–30% を既定で空けるやり方は採らない。予定と定期のあいだに TODO を詰め、小さな余りは「次の TODO の所要時間が入らないとき」にだけ残る。
- **タスクは三種類。** **予定**は事前に決まっていた単発で、開始時刻がある（例: 歯医者）。**TODO**は事前に決まっていない単発、または恒常的にあるが時刻は決まっていないもの。プール。所要時間があり、開始時刻はない。**定期**は事前に決まっている定常登録で、繰り返しと開始時刻がある（例: 犬の散歩、火・金の可燃ゴミ出し）。
- **予定と定期がカレンダーを先に占める。** TODO は、起床から「ここまで組む」までの空きに、生成が差し込む。
- **定期は自分の開始時刻を占める。** 犬の散歩を一日の末尾に固定しない。その日の最後は、その日に置かれたブロックのうち最も遅いものである。
- **「最初の一歩」は持たない。** ユーザーに書かせない。モデルにも出さない。必須にもしない。
- **やりたいことも TODO に含まれる。** 空きを埋める TODO に、ユーザーがやりたいことも入る。やりたいこと専用の枠や比率は持たない。
- **雨は、生成時にユーザーが伝え、項目の雨天中止で扱う。** ユーザーが自分で天気を見て、その日が雨かをはい／いいえで asuyaru に伝える。天気 API は使わない。予定、定期、TODO のいずれも、項目ごとに雨天中止フラグを持てる。フラグが無い項目は **雨天決行**（雨でも出す）。雨なら、雨天中止の項目はその日の時間割に置かない。定義とプールには残る。雨向き、短縮、代替などのモードは持たない。
- **割り当て時刻は、時間割の各ブロックが持つ。** 次のブロックへ押すこと自体はこの要件の対象外である。当日の組み直しもしない。飛ばしの扱いもしない。

---

## 成功の条件

1. **着手できる。** 休日の朝、時間割の最初のブロックを「何からやるか」で止まらずに始められる。動機づけは一日の最初の成果であり、消化の前段ではない。
2. **生活が落ちない。** 歯医者のような予定と、犬の散歩や可燃ゴミ出しのような定期が、やる気や気分で消えない。雨天決行の項目は、雨でも落ちない。
3. **休日が仕事化しない。** 空きを埋める TODO は、やらなきゃだけではない。やりたいことも同じプールから載る。クォータは持たない。
4. **雨の日は雨天中止だけが落ちる。** 雨かどうかは、生成時にユーザーが伝える。雨天決行はそのまま出る。天候アプリにも天気 API にもしない。
5. **組まれた一日に乗っかれる。** 前夜にできた時間割を、当日は追う。消化率 100% は成功条件ではない。この要件が出すのは、その時間割までである。

避けたい状態は、ゆるすぎて一日が間延びすること、予定と定期を無視して TODO だけで埋めること、朝から計画づくりに戻ってまた決められないこと、約束や定期が後回しになって生活が欠けること、雨なのに雨天中止の項目が載ること、雨天決行まで落とすことである。

---

## 対象ユーザー

主対象は、自分の休日を自分で決める一人の利用者である。

- 平日は仕事や学業があり、休日を自分のために使いたい。
- 「これやらなきゃ」「いつかやりたい」が頭に残り続け、休日になっても着手点が見えない。
- 細かく自己管理したい人というより、**組まれた時間割に乗りたい人**。
- その日の約束（歯医者など）と、曜日や時刻に紐づく生活の定期（犬の散歩、火・金の可燃ゴミ出しなど）がある。散歩は雨なら休み、ゴミ出しは雨でも出す、といった区別がある。

コピーは日本語のみ。
利用は個人のみ。
家族の時間割やチームの進捗は対象外である。

---

## コアループ

製品の中心は、前夜に時間割を組んで、当日は乗っかることである。
この要件が定めるのは、前夜の構築までである。

### TODO を預ける、予定を置く、定期を登録する

頭に浮かんだ「やらなきゃ／やりたい」を、開始時刻なし・所要時間ありの TODO として材料庫に入れる。
毎日手でカレンダーを埋める場所ではない。

名前と所要時間は必須とする。
雨天中止にするかは項目ごとに付ける。
細かい分類より、翌日の空きに差し込めることを優先する。
時刻は決まっていないがいつもありそうなことも、TODO である。

歯医者のような、事前に決まっていた単発は予定として置く。
開始時刻と所要時間を持つ。

犬の散歩やゴミ出しのような、事前に決まっている定常は定期として登録する。
開始時刻、所要時間、簡単な繰り返しと、必要なら雨天中止を持つ。

### 前夜に計画を作る

計画を作った日が休日である。
祝日カレンダーや週末判定は見ない。
連休でも、その夜は翌日一日分だけを作る。
翌日また計画を見る。

生成のとき、ユーザーが自分で天気を見て、その日は雨か（はい／いいえ）を伝える。
その日に当たる予定と、曜日などが一致する定期のうち、雨かつ雨天中止のものは置かない。
残りを開始時刻どおりに置き、空きに TODO（雨かつ雨天中止のものは除く）を差し込み、時刻つきの時間割を出す。
結果を一度見る。
先頭の違和感があれば差し替えてよい。
細かい並べ替え UI は主体験にしない。
見たら寝る。

### 休日当日

狙いは、時刻どおりに次へ進むことである。
この要件は、次のブロックへ促さない。
飛ばしたときの処理をしない。
残りを組み直さない。
天候が朝に変わっても、前夜の時間割を組み直さない。

### 夜

時間割に載らなかった TODO（雨天中止でその日外したもの含む）は材料庫に残る。
その日の予定は終わる。
定期の定義は、雨天中止でその日出さなくても残る。
連休の翌日分は、その夜にまた計画を作る。
新しい「やらなきゃ／やりたい」が浮かんだら、また TODO として預ける。

---

## 一日の時間枠と見え方

生成が使う一日の枠は、次の二つで決まる。
どちらもユーザーが設定する。

| 項目 | 意味 |
| --- | --- |
| 起床時刻 | その日の最初にブロックを置ける時刻 |
| ここまで組む | ブロックを置ける最も遅い時刻。就寝時刻ではない。この時刻より後ろには置かない |

出力は、開始時刻と終了時刻を持つ時間割である。
キューではない。

空きは、予定と定期を置いたあとの隙間である。
起床から最初のブロックまで、最後のブロックのあとから「ここまで組む」までを含む。
TODO はそこに、きつめに入る。
入らない TODO は載せない。
20–30% をあらかじめ空ける、という既定は持たない。

その日の最後のブロックは、置かれたもののうち終了が最も遅いものである。
特定の定期を末尾に固定しない。
雨で予定や定期が落ちたあとの空きも、TODO で埋めてよい。

予定または定期が「ここまで組む」に収まらないときは、消さずにユーザーに知らせる。

---

## タスクモデル

第一の分け方は **予定**、**TODO**、**定期** の三つである。
プロジェクト階層やサブタスクツリーは持たない。
一日に載らない大きさの TODO は、預けるときに分割する。
「最初の一歩」という項目は無い。

予定、定期、TODO は、いずれも **雨天中止**（オン／オフ）を持てる。
オフ（未設定）は **雨天決行** である。
屋内／屋外、雨向き、短縮、代替といった天候用の別モードは持たない。

### 予定

事前に決まっていた単発。
開始時刻と所要時間を持つ。
カレンダーを先に占める。
繰り返しは持たない。

| 項目 | 意味 |
| --- | --- |
| 名前 | 「歯医者」など |
| 開始時刻 | 必須。時計時刻 |
| 所要時間 | 必須。分単位。終了時刻は開始＋所要時間 |
| 雨天中止 | オンなら、その日が雨のとき時間割に置かない。オフなら雨天決行 |

- 例: その日の歯医者。雨天決行が普通である。
- 予定同士、または予定と定期が重なるときは、消さずにユーザーに知らせる。TODO のために予定を落とさない。

### TODO

事前に決まっていない単発、または恒常的にあるが時刻は決まっていないもの。
事前登録のプールである。
開始時刻は持たない。
生成が空きに差し込む。

| 項目 | 意味 |
| --- | --- |
| 名前 | 着手時に何をするか分かる名前 |
| 所要時間 | 必須。分単位。空きに入るかの判定に使う |
| 雨天中止 | オンなら、その日が雨のとき空きに入れない。オフなら雨天決行 |

やりたいことも、やらなきゃも、同じ TODO である。
ラベルで比率を取らない。
プールに入っているものが空きを埋める。
雨天中止でその日外した TODO はプールに残る。

任意のメモは、生成には使わない補足にしてよい。
開始のしやすさや期限感は、空きにどれを先に入れるかのヒントにしてよい。
第一の種別にはしない。
ユーザーに「最初の一歩」を書かせない。

やった／飛ばしたの記録は必須にしない。

時刻が決まって繰り返すものは定期として登録する。

### 定期

事前に決まっている定常登録。
定義は残り、計画を作った日のうちルールに合う日に、開始時刻どおり展開される。
雨天中止でその日出さなくても、定義は消えない。

| 項目 | 意味 |
| --- | --- |
| 名前 | 「犬の散歩」「可燃ゴミ出し」など |
| 開始時刻 | 必須。時計時刻 |
| 所要時間 | 必須。分単位。終了時刻は開始＋所要時間 |
| 繰り返し | 必須。単純なルール |
| 雨天中止 | オンなら、その日が雨のとき時間割に置かない。オフなら雨天決行 |

繰り返しは単純で足りる。

- 曜日（複数可）。例: 火・金。
- 計画を作った休日ごと、など同程度の単純さ。

複雑な RRULE（月の第 n 曜日、例外日の集合、間隔の合成など）は持たない。

終わったのはその日の回だけである。
連休の翌日も、その日の曜日がルールに合えばまた出る。
雨天中止でその日出さなくても、次にルールに合う日の回は別である。

- 例: 犬の散歩。開始時刻つきの定期。**雨天中止。** 一日の末尾である必要はない。
- 例: 可燃ゴミ出し。火・金だけの定期。**雨天決行。** 計画する日が火または金なら、雨でも出る。
- 定期同士、または定期と予定が重なるときは、消さずにユーザーに知らせる。TODO のために定期を落とさない。

---

## 天候

- 生成のとき、ユーザーが自分で天気を調べ、その日は雨か（はい／いいえ）を asuyaru に伝える。天気 API は使わない。
- 雨でない日は、雨天中止フラグを無視して通常どおり置く。
- 雨の日は、雨天中止の予定、定期、TODO をその日の時間割に置かない。雨天決行は置く。
- 置かなかった定期の定義は残る。置かなかった TODO はプールに残る。
- 当日朝に雨の判断が変わっても、組み直さない。

---

## 生成ルール

入力は、その日の予定、ルールに合う定期、TODO プール、ユーザーが伝えたその日は雨か（はい／いいえ）、起床時刻、「ここまで組む」時刻である。
出力は、開始時刻と終了時刻を持つ時間割である。

順:

1. **枠を取る。** 起床から「ここまで組む」まで。この枠より後ろには置かない。
2. **雨なら雨天中止を外す。** 予定、定期、TODO いずれも、雨かつ雨天中止ならその日は候補にしない。定義とプールは残す。雨でなければ、フラグは見ない。
3. **予定と定期を先に置く。** 残った予定と、その日の曜日などに合う定期を、それぞれの開始時刻どおりに置く。犬の散歩を末尾に予約しない。重なりは知らせる。落とすなら、知らせたうえで落とす。
4. **空きを TODO で埋める。** 予定と定期を置いたあとの隙間（起床直後、最後のブロックのあと〜「ここまで組む」を含む。雨で落ちたあとの空きも含む）に、所要時間が入る TODO を差し込む。開始時刻は、空きの先頭から順に割り当てる。きつめ。20–30% の余白を先に確保しない。入らない TODO は載せない。ダミーは出さない。
5. **やりたいことの扱い。** クォータは持たない。プールの TODO が空きを埋める。その中にやりたいことが含まれる。
6. **先頭。** 時間割の最初のブロックが着手点である。朝に予定または定期があればそれが先頭でよい。最初の空きに入れる TODO は、開始しやすいものを優先してよい。

材料が少なければ、予定と定期だけ、または短い時間割でよい。
あらかじめ空ける余白とは違う。

ユーザーが前夜にやってよい調整は、先頭の差し替えと、載せる／載せないの少数のオンオフである。
並べ替え UI を主体験にしない。

当日に飛ばしても、残りを再配置しない。
次のブロックへの催促もしない。

---

## データの持ち方

- データは **SQLite ファイル一つ** である。
- そのファイルをその Mac のローカルに置いて動いてよい。
- 同じファイルを iCloud 上に置き、複数 Mac がそれを共有できる。同期プロトコルを自前で持たない。ファイルが一つであることが共有の単位である。
- 保存先パスが差し替え可能な「ファイル一つ」から始める。複数ファイルや専用サーバーを前提にしない。

UI フレームワークや配布形態は、この文書の対象外である。

---

## 対象外

- 休日の自動検出（週末、祝日カレンダー、OS の休み判定）
- 連休全体の最適配分、複数日にまたがるスケジューリング
- 順番だけのキュー表示
- 余白 20–30% を既定で空ける組み方
- 「やりたいこと」専用の枠、比率、クォータ
- 「最初の一歩」の入力、表示、必須化
- 特定の項目を「一日の最後」に固定するフラグやルール（犬の散歩を末尾に固定することを含む）
- 複雑な RRULE
- 天候の追加モード（雨向き、短縮、代替、屋内外の別ラベル、降水確率の段階）
- 天気 API、天候アプリ化、当日朝の天候による組み直し
- 当日の残り一日の組み直し
- 飛ばしの扱い（スキップ後の再配置や代替）
- 時刻になったら次のブロックへ強制する／促す体験
- 仕事のプロジェクト管理、チーム共有、担当者、コメント、進捗レポート
- フル機能のカレンダー同期、会議の空き検索
- 習慣ストリーク、ポイント、ゲーム化
- チャットで計画を相談する体験、生成を会話にすること
- 家族、複数人の時間割の調整
- 日本語以外のローカライズ
- モバイルアプリ、ウェアラブル（対象は Mac）
- 家計、買い物リスト専用の機能
- ポモドーロ等のタイマー製品化
- アカウント、自前のクラウド同期、通知インフラ
- 就寝時刻を軸にした一日設計

## 未決（技術）

1. **デスクトップの実現手段。** Mac 向けデスクトップであることは決まっている。どの技術で作るかは未決である。保存は SQLite ファイル一つ、から始められる形に限る。
